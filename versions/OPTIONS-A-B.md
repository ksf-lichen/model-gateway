# 源模型录入方案 A / B 对比（兼顾灵活性 vs 操作简易性）

> 背景：目标是**模型级**可配不同折扣与费用；同时希望录入不繁琐。  
> 对照冻结版：`versions/v1/`。

---

## 方案 A — 数据模型保持 V1，向导改成「先供应商、再勾多模型」

**做法**：仍无「一条 source = 连接 + 模型 + prices」。  
添加时先填供应商连接（URL/Key），再勾选多个上游模型；每一行填/覆盖折扣与单价 → 批量生成多条 source。

| | 优势 | 劣势 |
|--|------|------|
| **灵活性** | 每模型独立 `prices`，与 V1 计费一致；忙闲时、绝对价、折扣都能按模型设 | 供应商级「默认折扣」没有一等公民字段（只能靠批量填同一折扣，或以后加可选「应用到全部」） |
| **简易性** | 同 Key 多模型不用反复填 URL/Key；学习成本低（概念仍是「源」） | 模型很多时，表格行仍要逐行确认价格 |
| **实现/迁移** | 几乎不改存储与计费；改向导即可；V1 数据可原样沿用 | 凭证轮换时要改多条 source（可加「同源 Key 同步」补丁） |
| **风险** | 低 | 若用户误以为「改了供应商折扣会自动改所有模型」——需文案说清是「生成时默认值」 |

---

## 方案 B — 独立 Provider 实体 +「供应商 × 模型」绑定价表

**做法**：Provider 只管连接与可选「默认折扣」；下面挂模型列表，每模型可覆盖价/折扣。计费读绑定层。

| | 优势 | 劣势 |
|--|------|------|
| **灵活性** | 供应商默认折扣 + 模型覆盖，三层清晰；轮换 Key、改 Base URL 一处生效 | 概念变多（Provider / 绑定 / 服务），和现控制台用词要对齐 |
| **简易性** | 日常「改账号」极省事；批量开模型也顺 | 首次理解成本高于 A；列表/详情要多一层导航 |
| **实现/迁移** | 更接近 OneGateway 等市面产品，后期插件/路由好挂 | 要迁 V1 source → Provider+绑定；计费、探测、用量归因都要改 |
| **风险** | 中长期扩展好 | 短期改动面大，原型迭代变慢 |

---

## 怎么选（你要的：灵活 + 好操作）

| 诉求 | 更贴哪边 |
|------|----------|
| 模型级不同折扣/费用 | **A、B 都能** |
| 少填几遍 Key/URL | **A、B 都能**（A 用向导批量建源即可） |
| 供应商默认折扣 + 单模型覆盖 | **B 更原生**；A 用「默认填入 + 行内改」也能模拟 |
| 少改代码、保 V1 可回退 | **A** |
| 长期对标企业网关控制台 | **B** |

### 建议（兼顾两者时的折中）

1. **下一版先做 A（可叫 V1.1）**：冻结 V1 数据模型不动，只改「添加」体验 → 灵活性不丢，操作明显变简单，风险最低。  
2. **若跑一段时间后**出现「经常整账号改折扣 / 轮换 Key」→ 再演进到 **B**，把多条同连接 source 收成 Provider，价表升到绑定层。

这样既照顾现在的灵活定价目标，又先拿操作简易性，避免过早上 B 的迁移成本。
